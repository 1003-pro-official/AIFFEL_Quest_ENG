## 3. 세부 퀘스트 수행 내용 (Quest Details)

### [미션 1] 머신러닝 시스템의 현실과 숨겨진 기술 부채 (Hidden Technical Debt)

* **문제 인식**:
  * 연구/실험 환경에서는 모델의 정확도(Accuracy)를 높이는 순수 알고리즘 코드 작성이 주를 이룹니다.
  * 그러나 실제 상용(Production) 시스템에서 **순수 머신러닝 코드는 전체 시스템의 5~10%에 불과**합니다.
* **숨겨진 기술 부채 (90% 이상의 엔지니어링 영역)**:
  * **데이터 수집 및 검증 (Data Collection & Verification)**: 실시간으로 유입되는 원천 데이터의 이상치 및 결측치 검증
  * **피처 엔지니어링 및 추출 (Feature Extraction)**: 모델이 학습할 수 있는 의미 있는 변수 가공
  * **인프라 및 자원 관리 (Resource Management)**: CPU/GPU 클러스터 분산 컴퓨팅 및 스케일링
  * **서빙 인프라 (Serving Infrastructure)**: 초당 수천 건의 요청을 지연 없이 처리하는 API 구축
  * **모니터링 및 분석 (Monitoring & Analysis)**: 데이터 분포 변화(Data Drift) 및 모델 성능 저하 추적
* **MLOps(Machine Learning Operations)의 정의**:
  * 머신러닝 모델의 개발(Dev)과 운영(Ops)을 통합하여, 모델 개발부터 배포, 모니터링, 재학습까지의 전 과정을 자동화하고 안정적으로 관리하는 엔지니어링 프랙티스입니다.

### [미션 2] 머신러닝 라이프사이클 7단계 (ML Lifecycle)

```text
[1단계] 문제 정의 (Business Problem)
   │
   ▼
[2단계] 데이터 수집 및 가공 (Data Engineering)
   │
   ▼
[3단계] 모델 개발 및 학습 (Model Training)
   │
   ▼
[4단계] 모델 평가 및 검증 (Model Evaluation)
   │
   ▼
[5단계] 모델 패키징 및 서빙 배포 (Packaging & Serving)
   │
   ▼
[6단계] 운영 및 성능 모니터링 (Monitoring & Logging)
   │
   ▼
[7단계] 지속적 재학습 (Continuous Training, CT)
   └───────────────> (1~2단계로 피드백 순환)
```

1. **문제 정의 (Problem Framing)**: 비즈니스 요구사항을 머신러닝 문제(분류, 회귀, 추천 등)로 정의하고 평가지표(KPI)를 수립합니다.
2. **데이터 수집 및 라벨링 (Data Engineering)**: 다양한 소스에서 데이터를 수집, 정제하고 학습용 피처셋을 구축합니다.
3. **모델 학습 (Model Training)**: 적합한 알고리즘을 선정하고 하이퍼파라미터 튜닝을 통해 모델을 학습시킵니다.
4. **모델 평가 (Evaluation)**: 검증 데이터셋을 통해 정확도, 정밀도, 재현율, 손실값 등을 다각도로 검증합니다.
5. **서빙 배포 (Serving & Deployment)**: 학습된 가중치와 전후처리 로직을 패키징하여 REST API 또는 배치 파이프라인으로 서빙합니다.
6. **모니터링 (Monitoring)**: 실제 운영 환경에서 들어오는 요청 로그와 레이턴시, 데이터 드리프트 현상을 실시간 감시합니다.
7. **지속적 학습 (Continuous Training)**: 축적된 최신 운영 로그를 기반으로 모델을 자동으로 재학습하여 성능을 유지합니다.

### [미션 3] 가상머신 (VM) vs Docker 컨테이너 가상화 비교

```text
[가상머신 (Virtual Machine) 구조]          [Docker 컨테이너 (Container) 구조]
+---------------------------------+       +---------------------------------+
| App 1 | App 2 | App 3           |       | App 1 | App 2 | App 3           |
+---------------------------------+       +---------------------------------+
| Guest OS (각각 수 GB 용량)       |       | Bins / Libs (격리된 종속성)      |
+---------------------------------+       +---------------------------------+
| Hypervisor (가상화 계층)         |       | Docker Engine (컨테이너 엔진)   |
+---------------------------------+       +---------------------------------+
| Host OS (호스트 운영체제)       |       | Host OS (호스트 커널 공유)      |
+---------------------------------+       +---------------------------------+
| Physical Server (하드웨어)      |       | Physical Server (하드웨어)      |
+---------------------------------+       +---------------------------------+
```

| 비교 항목 | 하이퍼바이저 기반 가상머신 (VM) | Docker 컨테이너 (Container) |
| :--- | :--- | :--- |
| **격리 수준** | 하드웨어 수준 격리 (완전 독립) | 프로세스 수준 격리 (OS 커널 공유) |
| **게스트 OS** | 각 VM마다 별도의 Guest OS 필요 | **Guest OS 없음 (호스트 커널 직접 사용)** |
| **용량 크기** | OS 이미지 포함으로 수 GB ~ 수십 GB | **수십 MB ~ 수백 MB (매우 가벼움)** |
| **부팅 속도** | OS 부팅 필요 (수십 초 ~ 수 분) | **프로세스 시작 속도 (수 밀리초 ~ 수 초)** |
| **자원 효율성** | CPU/RAM을 고정 할당하여 낭비 발생 | **필요한 만큼만 동적으로 메모리 점유** |
| **이식성** | 하이퍼바이저 환경에 종속적 | **어디서나 동일하게 실행 (Write Once, Run Anywhere)** |

### [미션 4] Docker 3대 구성 요소와 이미지 빌드 메커니즘

```text
+----------------+      docker build       +----------------+       docker run        +----------------+
|   Dockerfile   |  ───────────────────>   |  Docker Image  |  ───────────────────>   |   Container    |
| (텍스트 설계도)|                         |  (읽기 전용 빵틀) |                         | (독립 실행 인스턴스) |
+----------------+                         +----------------+                         +----------------+
```

1. **Dockerfile (설계도)**:
   * 베이스 이미지 지정(`FROM`), 패키지 설치(`RUN`), 소스코드 복사(`COPY`), 포트 개방(`EXPOSE`), 실행 명령어(`CMD`/`ENTRYPOINT`)를 텍스트로 기술한 파일입니다.
2. **Docker Image (불변의 템플릿)**:
   * Dockerfile을 빌드하여 생성된 읽기 전용(Read-only) 실행 패키지입니다. 레이어(Layer) 구조로 쌓여 중복 다운로드를 방지하고 캐시를 재사용합니다.
3. **Docker Container (실행 인스턴스)**:
   * 이미지를 기반으로 격리된 프로세스 환경에서 실제 동작하는 상태입니다. 하나의 이미지로부터 여러 개의 독립된 컨테이너를 생성하고 삭제할 수 있습니다.

## 4. 퀘스트 결론 및 핵심 요약 (Summary)

* MLOps는 머신러닝의 90%를 차지하는 복잡한 시스템 기술 부채를 해결하기 위한 필수적인 문화이자 엔지니어링 체계입니다.
* 머신러닝 모델의 라이프사이클은 단순히 학습에서 끝나지 않고, 서빙 배포와 모니터링을 거쳐 지속적 학습(CT)으로 끊임없이 순환해야 합니다.
* Docker 컨테이너는 OS 커널을 공유하는 가벼운 가상화 기술로, "내 컴퓨터에서는 잘 되는데 서버에서는 안 되는 문제"를 원천 해결하여 MLOps 배포의 핵심 표준 도구로 사용됩니다.
