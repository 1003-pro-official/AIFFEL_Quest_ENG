## 2. 각 섹션 체크포인트 답변 정리

### 2.1 [섹션 1 체크포인트] 프로젝트 개요 및 텍스트 생성 서빙

#### Q1. Day 5(정형 데이터 회귀)와 Day 7(텍스트 생성)에서 전처리가 어떻게 다릅니까?
* 답변:
  * Day 5(정형 데이터): 수치형/범주형 데이터를 처리하기 위해 StandardScaler(표준화), One-Hot Encoding, 결측치 대체(Imputation) 등의 전처리를 수행하여 2차원 고정 크기 행렬(텐서)로 변환합니다.
  * Day 7(텍스트 생성): 자연어 문장을 처리하기 위해 사전 학습된 토크나이저(Tokenizer)를 사용하여 문자열을 서브워드 정수 토큰 ID 리스트(input_ids, attention_mask)로 변환(Encoding)하고, 역할별 템플릿(<|im_start|>role\ncontent<|im_end|>)을 주입하는 전처리를 수행합니다.

#### Q2. Hugging Face Transformers 라이브러리의 역할은 무엇입니까?
* 답변:
  * 수만 개 이상의 사전 학습된 최신 딥러닝 모델(BERT, GPT, Qwen, Llama 등)과 토크나이저를 단 몇 줄의 통일된 고수준 API(AutoModelForCausalLM, AutoTokenizer)로 손쉽게 다운로드, 캐싱, 로드, 추론 및 텍스트 생성 파이프라인으로 연결해 주는 표준 오픈소스 프레임워크입니다.

### 2.2 [섹션 2 체크포인트] Hugging Face 모델 로드 및 텍스트 생성

#### Q1. 토크나이저의 encode()와 decode()는 각각 무엇을 합니까?
* 답변:
  * encode() (또는 tokenizer(...)): 사람이 읽는 텍스트 문자열을 모델이 연산할 수 있는 정수 토큰 ID 배열(input_ids 텐서)로 변환합니다.
  * decode(): 모델의 출력 결과인 숫자 토큰 ID 텐서를 다시 사람이 읽을 수 있는 자연어 텍스트 문자열로 복원합니다.

#### Q2. apply_chat_template()은 왜 필요합니까? 직접 프롬프트를 만들면 안 됩니까?
* 답변:
  * 각 LLM 모델(Qwen, Llama, ChatGLM, Mistral 등)마다 인스트럭션 튜닝 시 사용한 특수 토큰과 대화 구분자 형식(예: ChatML의 <|im_start|>user\n...<|im_end|>)이 서로 다릅니다.
  * apply_chat_template()은 모델의 메타데이터에 정의된 Jinja 템플릿을 자동으로 적용하여 모델이 훈련받은 형식과 100% 일치하는 프롬프트를 구성해 주므로, 수동 작성 시 발생할 수 있는 오타나 특수 토큰 불일치로 인한 생성 품질 저하를 방지합니다.

### 2.3 [섹션 3 체크포인트] FastAPI 챗봇 백엔드 스키마 및 서버 설계

#### Q1. ChatRequest의 messages가 리스트인 이유는 무엇입니까?
* 답변:
  * 챗봇이 직전 질문뿐만 아니라 이전 대화의 맥락(Context)을 기억하고 연속적인 대화(멀티턴 대화)를 이어갈 수 있도록 [{"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}] 형태의 전체 대화 히스토리를 전달받아야 하기 때문입니다.

#### Q2. 서버가 대화 기록을 저장하지 않고, 클라이언트가 매번 전체 기록을 보내는 이유는?
* 답변:
  * 무상태(Stateless) 아키텍처를 유지하기 위함입니다.
  * 서버가 세션이나 상태를 보관하면 서버 메모리 부하가 증가하고, 다중 인스턴스로 수평 확장(Scale-out) 시 세션 동기화(Sticky Session, Redis 등)가 복잡해집니다. 클라이언트가 대화 기록을 전송하게 하면 서버는 단순 연산만 수행하므로 장애 복구와 확장이 매우 용이해집니다.

#### Q3. max_new_tokens는 무엇을 제한합니까? 입력 토큰도 포함됩니까?
* 답변:
  * 모델이 새롭게 생성할 출력 텍스트의 최대 토큰 수만을 제한합니다.
  * 사용자가 보낸 기존 입력 프롬프트(입력 토큰 수)는 포함되지 않으며, 모델이 출력을 생성하다가 이 토큰 수에 도달하면 생성을 강제 종료합니다.

### 2.4 [섹션 4 체크포인트] Streamlit UI 채팅 인터페이스

#### Q1. st.chat_message와 st.chat_input은 각각 어떤 역할을 합니까?
* 답변:
  * st.chat_input: 사용자로부터 채팅 입력을 받는 UI 위젯으로, 엔터 키를 누르면 입력된 텍스트를 반환하고 화면을 다시 렌더링합니다.
  * st.chat_message: "user" 또는 "assistant" 역할에 맞게 아바타 아이콘과 함께 대화 말풍선 컨테이너를 생성하여 시각적으로 깔끔한 채팅 인터페이스를 구성합니다.

#### Q2. st.session_state["chat_messages"]에 대화 기록을 저장하는 이유는?
* 답변:
  * Streamlit은 사용자의 인터랙션(버튼 클릭, 텍스트 입력 등)이 발생할 때마다 전체 파이썬 스크립트를 처음부터 다시 실행(Rerun)합니다. 따라서 일반 변수에 저장하면 이전 대화가 모두 초기화되므로, 세션이 유지되는 동안 데이터를 영구 보존하기 위해 st.session_state를 사용합니다.

#### Q3. "대화 초기화" 버튼이 st.rerun()을 호출하는 이유는 무엇입니까?
* 답변:
  * 세션 상태 변수 st.session_state["chat_messages"] = []로 비운 후, 변경된 빈 대화 상태를 화면에 즉각 반영하여 이전 말풍선들을 깨끗하게 지우기 위해 화면 강제 재실행(st.rerun())을 호출합니다.

### 2.6 [Day 7 최종 체크포인트] 5대 핵심 질문 상세 답변

#### Q1. Day 5(정형 데이터)와 Day 7(텍스트 생성)에서 전처리 방식의 차이는?
* 답변:
  * Day 5는 테이블형 수치/범주 데이터를 다루므로 스케일링(StandardScaler)과 결측치 처리 및 원-핫 인코딩을 거쳐 고정 차원 텐서로 변환합니다.
  * Day 7은 가변 길이의 텍스트를 다루므로 토크나이저를 통해 서브워드 토큰화, 어휘 사전 인덱싱(input_ids), 패딩/마스킹(attention_mask), ChatML 대화 템플릿 결합을 수행합니다.

#### Q2. 멀티턴 대화에서 서버가 상태를 유지하지 않는 이유는?
* 답변:
  * 무상태(Stateless) 구조를 통해 서버의 메모리 부하를 방지하고, 수평 확장(Horizontal Scaling) 및 로드 밸런싱 환경에서 어떤 서버 인스턴스로 요청이 유입되어도 동일하게 처리할 수 있도록 시스템 안정성과 확장성을 극대화하기 위함입니다.

#### Q3. API Key가 잘못되면 서버는 어떤 상태 코드를 반환하고, UI는 어떻게 처리합니까?
* 답변:
  * 서버는 401 Unauthorized 상태 코드와 세부 에러 메시지({"detail": "..."})를 반환합니다.
  * UI(Streamlit)는 이를 감지하여 불필요한 모델 추론 대기 없이 즉시 사용자에게 API 키 오류 메시지를 출력하고 사이드바에서 키 수정을 유도합니다.

#### Q4. temperature를 낮추면 생성 결과에 어떤 변화가 있습니까?
* 답변:
  * temperature가 낮아질수록(예: 0.1~0.2) 다음 토큰 확률 분포의 차이가 극대화되어 가장 확률이 높은 단어만 선택(Greedy에 가까워짐)되므로, 출력이 매우 결정론적이고 일관되며 논리적/보수적으로 변합니다. 반대로 높이면 창의적이고 다양한 단어가 선택됩니다.

#### Q5. 이 서비스를 다른 컴퓨터에서 실행하려면 무엇이 필요합니까?
* 답변:
  1. Python 가상환경 및 의존성 패키지: requirements.txt (fastapi, uvicorn, streamlit, torch, transformers, chromadb, sentence-transformers 등).
  2. 프로젝트 소스 코드: app/ (API, 스키마, 모델, RAG 엔진) 및 frontend/ (Streamlit 대시보드).
  3. Hugging Face 모델 캐시 / 다운로드 환경: 인터넷 연결 또는 사전 다운로드된 모델 가중치.
  4. 포트 개방: FastAPI 백엔드(8000), Streamlit 프론트엔드(8501).

### 3.2 Problem (마주친 문제점 및 해결 과정)
* 문제 1: Windows 환경 인코딩 충돌 (cp949 및 latin-1 헤더 에러)
  - 원인: Windows 기본 콘솔 인코딩(cp949)과 HTTP 헤더 전송 시 한글 메타데이터(X-User: 사용자A, X-Citations)가 표준 RFC 규격(ASCII/Latin-1)과 충돌하여 내부 500 에러가 발생했습니다.
  - 해결: sys.stdout.reconfigure(encoding='utf-8') 적용 및 urllib.parse.quote와 ensure_ascii=True를 적용하여 모든 HTTP 헤더를 안전한 ASCII 포맷으로 직렬화/역직렬화 처리했습니다.
* 문제 2: 포트 8000 잔존 프로세스로 인한 엔드포인트 404 에러
  - 원인: 백그라운드 주피터 커널 또는 이전 서버 프로세스가 8000 포트를 점유하고 있어 신규 /chat/stream 엔드포인트를 찾지 못했습니다.
  - 해결: PowerShell Get-NetTCPConnection으로 PID를 확인하여 프로세스를 종료하고 최신 v2 서버로 재기동하였으며, 프론트엔드에 구버전 404 자동 Fallback 메커니즘을 추가하여 안정성을 확보했습니다.
